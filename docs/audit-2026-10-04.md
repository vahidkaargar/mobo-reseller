# mobo-reseller audit, 2026-10-04 (main @ 47b9f98)

Read-only review of every layer: security, money and order flow, catalog and supplier, UI, infra/tests/CI. No code was changed during the review.
Severity: P0 = broken or loses money now; P1 = security or money risk; P2 = correctness/ops debt; P3 = cleanup.
"Confirmed" = code path read end to end (and re-checked by hand where marked ✔). "Suspected" = needs runtime or supplier confirmation.

## P1: money and order flow

| ID | Where | Problem | Fix direction |
|---|---|---|---|
| M-1 | `Order.php:59,68`; `CheckoutService.php:85` | The wallet package returns a REJECTED transaction without throwing. Results are never checked, so a rejected unlock followed by a successful withdraw marks the order SUCCEEDED with the reservation stuck. | Assert APPROVED after every lock, unlock and withdraw. |
| M-2 | `PlaceSupplierOrder.php:60-62` | Catches all `Throwable`, including Bamboo 401 and 422. A definite rejection then polls for 20 minutes and ends PROCESSING with funds locked. | On 401/422: unlock and mark FAILED. Poll only on network errors and 5xx. |
| M-3 ✔ | `PlaceSupplierOrder` (no `$timeout`), SDK timeout 160 s, `retry_after` 90 | A slow Bamboo call outlives the worker timeout. The job dies after status=PROCESSING but before the poller is queued, leaving the order stuck with no log. | Queue the poll before calling Bamboo; set `$timeout` and `retry_after` coherently; add a scheduled sweeper. |
| M-4 | `OrderResolutionService.php:58`, admin orders filter | A CREATED order whose job never ran (worker down) is excluded from "Needs attention" and cannot be resolved, so its funds stay locked forever. | Make CREATED orders older than N minutes resolvable. |
| M-5 | `SyncSupplierOrder` | No `failed()`. If `handle()` throws (for example in `chargeFunds`), the poll chain stops silently. | Add `failed()` plus a sweeper. |
| M-6 ✔ | `CartService.php:33` | The cart key `md5(base64(supplier.productId.purchase))` has no separator. Product 1 at 250 and product 12 at 50 collide, and the second add overwrites the first line. | Use `json_encode([...])` as the key input. |
| M-7 | `numbers_helper.php:27,35`, `CheckoutService.php:128-130`, `orders/create:200-225` | Rounded twice (4 dp, then 2 dp), so cents can drift. The page multiplies a pre-rounded unit, so the displayed total can differ from the locked amount. | Convert at full precision; round once per line. |
| M-8 | `CheckoutService` | Only `InsufficientFundsException` is mapped. InvalidAmount, a missing FX rate, an unknown supplier and TypeError all surface as 500s. | Map them to `CheckoutException`. |
| M-9 | `CheckoutService.php:59,93` | The cart is emptied after the SQL commit, so a line added in another tab in between is lost. If the Mongo save fails, the cart stays full and the user can re-order. | Compare-and-set against the snapshot that was read. |
| M-10 | `QUEUE_CONNECTION=sync` (phpunit) | Under `sync`, delays are ignored, so polling recurses up to 40 times inside one request and the FX refresh calls HTTP inline. | Refuse these dispatches on `sync` outside tests. |
| M-11 | `wallets/index:217-219` | The "Balance" headline is `available_funds`, which includes credit, but credit cannot fund orders. | Show balance minus locked as "spendable for orders". |
| M-12 | `Order::releaseFunds` | Unlocks against the aggregate `locked` without checking that this order's LOCK exists and is still open. This is what enables the double settlement in P0-5. | Look up LOCK and UNLOCK by reference inside the transaction. |

Verified OK: checkout recomputes all prices server-side. A per-user lock stops double checkout. Order, items and lock are created in one transaction. The wallet package uses `lockForUpdate`. The RequestId is deterministic. `PlaceSupplierOrder.failed()` only releases while the order is CREATED. Bamboo response caching is off.
